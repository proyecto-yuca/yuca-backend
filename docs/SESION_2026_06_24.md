## 4. Sistema de Permisos

### Estructura de tablas

```
roles
  id, identificador (unique), nombre, descripcion, sistema (bool)

modulos
  id, identificador (unique), nombre, orden

permisos
  id, rol_id, modulo_id, ver, crear, editar, eliminar (todos bool, default false)

users
  + rol_id (FK → roles, nullable)
  + estado  (bool, NOT NULL, default true)
```

### Roles del sistema (seed)

|---------------|---------------|----------------------------------------------------|
| `admin`       | Administrador | Todo (`ver + crear + editar + eliminar`) en todos los módulos |

| `owner`       | Propietario   | Gestión completa en `fincas`, `sensores`, `mediciones`; sin acceso al resto |
| `user`        | Usuario       | Sin permisos                                       |

### Módulos del sistema (8)

`inicio` · `fincas` · `cultivos` · `sensores` · `variables` · `mediciones` · `permisos` · `usuarios`

### PermissionGuard (`app/controllers/concerns/permission_guard.rb`)

Concern incluido en `BaseController` y `SessionsController`.

- `require_permiso(modulo, operacion)` — devuelve `403` si el usuario no tiene el permiso. **Los permisos siempre se leen de la DB**, no hay shortcut por rol.
- `permisos_del_usuario(user)` — construye la matriz completa para incluirla en el login.
- `permisos_cache` — cachea los permisos del request actual (variable de instancia).

| DELETE | `/api/v1/usuarios/:id`                | `usuarios:eliminar`  |

### Reglas de negocio

- Un usuario **no puede eliminarse a sí mismo**.
- Un usuario **no puede cambiar su propio estado**.
- `toggle_estado` alterna `estado: true ↔ false`.
- `cambiar_password` requiere `password` + `password_confirmation`.

### Campo `estado` en usuarios

- Columna `boolean NOT NULL DEFAULT true` en la tabla `users`.
- Incluida en `UserBlueprint` y en `UsuariosController#serialize_usuario`.

## 6. Visibilidad global por rol (fincas, cultivos, sensores, lecturas, IoT)

### Regla

| Rol          | Qué ve en `/api/v1/fincas`                       |
|--------------|--------------------------------------------------|
| `admin`      | Todas las fincas del sistema                     |
| `consultant` | Todas las fincas del sistema                     |
| `owner`      | Solo sus propias fincas                          |
| `user`       | Solo sus propias fincas                          |

### Filtro opcional para admin / consultant

```
GET /api/v1/fincas?user_id=3   →  solo fincas del usuario 3
```

### Implementación

Método `finca_scope` en `BaseController`:

```ruby
def finca_scope
  rol = current_user.rol&.identificador
  if rol.in?(%w[admin consultant])
    scope = Finca.all
    scope = scope.where(user_id: params[:user_id]) if params[:user_id].present?
    scope
  else
    current_user.fincas
  end
end
```

Se usa en todos los `set_finca` de:
- `FincasController`
- `CultivosController`
- `SensoresController`
- `LecturasSensorController`
- `Iot::CredentialsController`

Los permisos de operación (`crear`, `editar`, `eliminar`) se respetan independientemente — un consultor ve todas las fincas pero recibe `403` si intenta editar.

## 7. Seeds

Archivo: `db/seeds/permisos.rb` cargado desde `db/seeds.rb`.

Orden de limpieza en seeds (para evitar FK violations):

```
Permiso → SensorVariable → Sensor → LecturaSensor → IotCredential → Cultivo → Finca → User → Modulo → Rol
```

El seed usa `find_or_initialize_by + assign_attributes + save!` (no `find_or_create_by`) para garantizar que los datos se actualicen en corridas subsecuentes.

Al finalizar, asigna el rol `admin` a todos los usuarios existentes sin rol.

## 8. Decisiones de diseño tomadas

| Decisión | Motivo |
|----------|--------|
| `self.table_name` en modelos con nombre español | Rails pluraliza en inglés (`Sensor→sensors`, `Rol→rols`) |
| `foreign_key: { to_table: :roles/sensores }` | Misma razón: FK debe apuntar al nombre real de la tabla |
| Sin shortcut de admin en permisos | Permisos 100% desde DB para que el frontend los controle |
| `finca_scope` en BaseController (no en cada controller) | DRY: 5 controllers comparten la misma lógica de visibilidad |
| `UsuariosController` separado de `RegistrationsController` | Registro es público; gestión de usuarios es admin-only |
