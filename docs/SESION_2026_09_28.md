## 1. Motivación

La finca solo tenía `coordenadas`, un texto libre (ej. `"4.3372° N, 74.3641° W"`) que no sirve para dibujar un área. Los cultivos ya tenían `puntos_ubicacion` (hasta 4 vértices `{lat, lng}`), pero nada garantizaba que quedaran dentro de la finca.

Objetivo:
- La finca tiene sus propios puntos (hasta 4) y se pueden dibujar en el mapa.
- Los puntos de cada cultivo deben quedar **dentro** del polígono de la finca, validado en el backend (antes, la regla equivalente sensor/cultivo solo vivía en el frontend).

## 3. Concern `PuntosUbicacion` (nuevo)

`app/models/concerns/puntos_ubicacion.rb` — compartido por `Finca` y `Cultivo`.

| Método | Descripción |
|--------|-------------|
| `puntos_ubicacion_validos` (validación) | Arreglo, máximo 4 puntos (`MAX_PUNTOS`), `lat` y `lng` numéricos. Movida desde `Cultivo`, mismos mensajes de error. |
| `poligono` | Puntos como `Float` ordenados angularmente alrededor del centroide. `[]` si hay menos de 3 puntos. |
| `contiene_punto?(lat, lng)` | Ray casting sobre `poligono`. |
| `puntos_ubicacion_con_formato_valido?` (privado) | Evita correr la contención cuando el formato ya es inválido. |

La geometría es un port directo de `yuca-frontend/src/lib/mapGeometry.ts` (`orderPolygonPoints`, `isPointInPolygon`), para que backend y frontend den exactamente el mismo resultado aunque los vértices se envíen en cualquier orden.

## 4. Validaciones de contención

### `Cultivo#dentro_de_la_finca`

Si la finca tiene polígono (≥ 3 puntos), cada punto del cultivo debe quedar dentro:

```json
{ "errors": { "puntos_ubicacion": ["punto 3 está fuera del área de la finca"] } }
```

Si la finca no tiene área definida, no se valida (compatibilidad con fincas existentes).

### `Finca#cultivos_dentro_del_poligono`

Solo corre cuando cambia `puntos_ubicacion` en una finca ya persistida. Si el nuevo polígono deja algún cultivo fuera:

```json
{ "errors": { "puntos_ubicacion": ["el cultivo Lote Norte quedaría fuera del área de la finca"] } }
```

## 5. API — `FincasController`

- `finca_params` acepta `puntos_ubicacion: [ :lat, :lng ]` (top-level dentro de `finca`, igual que cultivos).
- `serialize_finca` devuelve `puntosUbicacion` con `lat`/`lng` como `float`.

```json
"puntosUbicacion": [
  { "lat": 3.543,  "lng": -76.3065 },
  { "lat": 3.543,  "lng": -76.301 },
  { "lat": 3.5345, "lng": -76.301 },
  { "lat": 3.5345, "lng": -76.3065 }
]
```

Enviar `puntos_ubicacion` reemplaza todos los puntos; `[]` los limpia.

Documentación actualizada: [`docs/api/v1/fincas/INTEGRATION.md`](./api/v1/fincas/INTEGRATION.md) y [`docs/api/v1/cultivos/INTEGRATION.md`](./api/v1/cultivos/INTEGRATION.md).

## 9. Decisiones de diseño tomadas

| Decisión | Motivo |
|----------|--------|
| `puntos_ubicacion` de finca opcional en backend | Las fincas existentes no tienen área; el formulario del frontend sí exige 3–4 puntos |
| Contención solo con ≥ 3 puntos | Con menos puntos no hay polígono que evaluar |
| Validar en backend además del frontend | El frontend puede saltarse; la regla de negocio debe vivir en el modelo |
| Validación de la finca solo si cambió el área | Evita recorrer cultivos en cada update de datos del dueño o ubicación |
| Mismo algoritmo que el frontend (orden angular + ray casting) | Backend y frontend nunca discrepan sobre si un punto está dentro |
| Concern compartido en vez de duplicar la validación | Finca y cultivo tienen exactamente las mismas reglas de formato |
